La distinción que no puede perderse

Elasticsearch no significa “búsqueda lexical”

Mecanismo

Lexical

texto → tokens → índice invertido → BM25

Muy fuerte para términos exactos, códigos, nombres y vocabulario compartido.

Mecanismo

Semántico

texto → embedding → vecinos → Top-k

Útil cuando consulta y documento expresan ideas parecidas con palabras diferentes.

OJO. Elasticsearch puede implementar ambos mecanismos y combinarlos. MongoDB Atlas también puede hacer Vector Search. La herramienta no define la idea.

Checkpoint 2

Embedding no es “resumen convertido a números”

El modelo genera una representación de 384 dimensiones. Lo importante hoy no es interpretar cada componente, sino comparar vectores en el mismo espacio.

ObservasInterpretación válidaInterpretación inválida
shape (n, 384)n documentos, 384 componentes384 conceptos humanos identificables
coseno 0.91alta cercanía bajo esta representación91 % de probabilidad de relevancia
Marca C2 cuando puedas explicar vector, dimensión y coseno sin usar la palabra “probabilidad”.
Checkpoint 3

Compara la misma consulta, no dos demos distintas

Ejecuta las tres consultas preparadas y mira el Top-5 de BM25 y el Top-5 semántico.

Busca una ganancia semántica

Un resultado defendible que aparezca mejor por paráfrasis o vocabulario distinto.

Busca un error semántico

Un documento “parecido” que tú no defenderías como relevante.

No declares ganador general. Un ID exacto favorece lexical; una paráfrasis puede favorecer semántica; muchas búsquedas reales combinan señales.
Marca C3 cuando hayas leído y comparado resultados, no solo scores.
Checkpoint 4

¿Por qué una base vectorial si NumPy ya funciona?

documento + embedding + metadata → persistencia → índice vectorial → consulta → vecinos

Con ~2 mil documentos, buscar exactamente en memoria es suficiente para aprender. La base aparece por persistencia, filtros, volumen, concurrencia y latencia.

ComponenteResponsabilidad

MongoDBpersiste documento + vector + metadata
