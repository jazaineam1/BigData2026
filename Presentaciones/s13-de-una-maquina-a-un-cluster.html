S13 · 05 · CPU y ejecución

¿Cuántos workers caben en un procesador de cuatro núcleos?

Núcleo, CPU lógica, proceso, worker e hilo

Núcleo físico: unidad de cómputo del procesador. CPU lógica o vCPU: unidad que el sistema puede planificar; cuatro vCPU no siempre equivalen a cuatro núcleos físicos.

Worker: proceso de Dask que ejecuta tareas. Hilo: unidad de ejecución dentro de ese worker. Scheduler: asigna tareas. Partición: fragmento de datos. Nodo: máquina física o virtual; una misma VM puede contener muchos workers.

Ejemplo con 4 vCPUConfiguración¿Qué significa?
1 worker1 proceso × 4 hilosUn proceso con cuatro hilos; depende del GIL y la tarea
2 workers2 procesos × 2 hilosDos procesos y hasta cuatro hilos
4 workers4 procesos × 1 hiloCuatro procesos independientes
8 workers8 procesos × 1 hiloPosible, pero excede las 4 vCPU: compiten por CPU y RAM

No existe un límite fijo de workers igual a núcleos. Puedes crear más workers, pero su velocidad puede empeorar. Para Python puro suele ser útil usar procesos; para NumPy, los hilos pueden aprovechar código nativo.

Concepto, ejemplo y limitación

HDFS (Hadoop Distributed File System) reparte archivos en bloques y almacena copias según un factor de replicación. Si un nodo deja de estar disponible, otro puede servir los bloques que conserva.

S13 · 07 · MapReduce

Un promedio de promedios puede ser falso

Motivo, fórmula y recorrido

Map transforma cada lote en estadísticas parciales; Shuffle reúne por clave; Reduce combina sumas y cantidades. Para una media global no basta promediar las medias de cada lote: sus tamaños son distintos.

media = (Σ suma parcial) / (Σ número de casos)
def map_lote(valores):
    return sum(valores), len(valores)
parciales = [map_lote(x) for x in lotes]
media = sum(s for s,n in parciales) / sum(n for s,n in parciales)

Este cálculo es reproducible con Python. Un framework distribuido automatiza partición, envío y combinación, no corrige una fórmula equivocada.

S13 · 10 · pandas frente a Dask

Misma consulta, dos motores; una referencia verificable

pandas: resultado de referencia

import pandas as pd
a = pd.read_csv('Cuadernos/datos/secop_chunks/prueba_chunk_0000000.csv')
a = a.drop_duplicates('id_del_proceso')

groupby: agrupa filas con la misma clave. size: cuenta registros por grupo, incluyendo valores nulos según configuración del grupo. sort_index: ordena claves para compararlas.

Dask DataFrame: ejecutar tras construir el grafo

import dask.dataframe as dd
d = dd.from_pandas(a, npartitions=4)
pendiente = d.groupby('modalidad_de_contratacion').size()
conteo_dask = pendiente.compute().sort_index()
# Normaliza tipos de índice: Arrow string en Dask y object en pandas.
def como_conteos(s):
    return {str(clave): int(valor) for clave, valor in s.items()}
assert como_conteos(conteo) == como_conteos(conteo_dask)

npartitions: número de fragmentos lógicos. compute: dispara las tareas diferidas y devuelve resultado a memoria local.

Prueba crucial: el assert certifica el mismo resultado, no que Dask sea más rápido.

Interpretar

Cómo se lee: mismo conteo por modalidad. Qué nos dice: motores equivalentes para esta agregación. Qué NO permite concluir: ventaja universal de tiempo. Error: confundir API similar con ejecución idéntica.

S13 · 11 · Ejecución diferida

Dask: crear un grafo no equivale a ejecutar

La idea en tres pasos

  1. Construir: describe operaciones (read → filter → groupby → sum).
  2. Planificar: un scheduler identifica dependencias y workers libres.
  3. Materializar: compute() o persist() inicia el trabajo y espera o conserva resultados.

Persistencia: persist() busca mantener resultados distribuidos, útiles cuando se reutilizan varias veces. No debe confundirse con escribir Parquet a disco.

S13 · 12 · Tiempo y recursos

El scheduler también cuesta tiempo: ¿cuándo se recupera?

Dos mediciones diferentes

Tiempo del cálculo (clúster caliente): cuánto tardan las tareas una vez que Dask ya tiene trabajadores listos. Tiempo de primera ejecución: arranque del scheduler y los workers + envío de tareas + cómputo + reunión de resultados.

Para trabajos cortos, la apertura puede costar más que lo ahorrado. Para un servicio que procesa lotes durante todo el día, el clúster puede quedarse abierto y reutilizarse.

Aceleración total = tiempo secuencial / tiempo Dask total

Mayor que 1 significa que Dask ganó **en la medición específica**. No debemos extrapolar resultados de una VM a otra.

S13 · 14 · Para qué sirve TF-IDF

¿Por qué convertimos las palabras en números TF-IDF?

El problema que realmente resuelve

Un documento SECOP dice «mantenimiento de computadores» y otro «mantenimiento de vías». Para buscar fichas parecidas o entrenar un clasificador, la computadora necesita una representación numérica de sus palabras.

TF (frecuencia de término) cuenta cuántas veces aparece una palabra en una ficha. DF (frecuencia documental) cuenta en cuántas fichas del conjunto aparece. IDF (frecuencia inversa) da más peso a palabras presentes en pocas fichas. TF-IDF multiplica frecuencia y peso; L2 normaliza el vector para compararlo sin que una ficha larga domine por tener más palabras.

IDF = ln[(1 + número de documentos)/(1 + DF)] + 1

Es la fórmula suavizada de scikit-learn. Las palabras comunes (como «servicio») ayudan menos a distinguir documentos; expresiones específicas pueden ayudar más.

Ejemplo completo para tres fichas

A: mantenimiento computadores
B: infraestructura computadores
C: hospital mantenimiento
TérminoDocumentos donde aparece (DF)IDF
computadoresA y B → 21,2877
mantenimientoA y C → 21,2877
hospitalsolo C → 11,6931
infraestructurasolo B → 11,6931

¿Por qué «hospital» vale más? Solo aparece en una ficha y distingue mejor un asunto hospitalario. Pero en A, su TF es cero y su peso final también es cero.

Objetivo del ejercicio: construir los vectores con los que luego calcularemos similitud coseno y clasificaremos textos. Dask puede repartir la transformación de muchos textos; TF-IDF y Dask resuelven problemas diferentes.

Una regla para interpretar

TF-IDF no comprende el significado como un modelo neuronal; transforma la evidencia lexical en números. Su utilidad es comparar documentos y alimentar algoritmos, no establecer verdades jurídicas.

S13 · 15 · Herramienta de texto

Calcula TF-IDF y lee la tabla columna por columna

Herramienta editable · resultados ordenados

Pulsa Calcular para crear la tabla con valores reales del minicorpus.

Qué significa cada columna

ColumnaInterpretación para ficha A
TérminoPalabra del vocabulario total
DFEn cuántas de las tres fichas aparece
IDFImportancia por frecuencia inversa; >1 si no aparece en todas
TF(A)Veces que aparece en A; puede ser 0
TF × IDF(A)Peso antes de normalizar
L2(A)Peso final normalizado del vector A

Ejemplo: «computadores» y «mantenimiento» aparecen una vez en A y tienen IDF 1,2877, por lo que ambos pesos L2 son 0,7071. «Hospital» tiene IDF 1,6931, pero al no aparecer en A su peso es cero.

Norma L2: la raíz de la suma de cuadrados de pesos; divide todos los pesos de A por su norma. No es un nuevo tipo de dato ni un tiempo de ejecución.

Prueba repetir «mantenimiento» en A: cambia TF y el peso normalizado de A, pero no DF.

Cómo saber si lo entendiste

Modifica una palabra en B y calcula nuevamente. La tabla muestra DF del conjunto completo, mientras TF y L2 corresponden solo a A. Esta separación evita confundir corpus y documento.

S13 · 17 · Similitud coseno

Búsqueda: recuperar documentos sin entrenar

Qué es un vector y qué mide el coseno

Un vector es una lista ordenada de números que representa una entrada. En TF-IDF, cada dimensión corresponde a un término del vocabulario. El coseno compara la orientación de dos vectores:

cos(A,B) = (A · B) / (||A|| × ||B||)

Con TF-IDF normalizado L2 y pesos no negativos, el coseno suele quedar entre 0 y 1. 1 significa misma dirección, no identidad contractual; 0 indica ausencia de términos compartidos bajo esa representación.

q = vectorizador.transform([consulta])
scores = cosine_similarity(q, matriz_documentos).ravel()
orden = np.argsort(scores)[::-1]

S13 · 18 · Evitar fuga

fit y transform: el test no puede enseñar al modelo

Aprende primero, evalúa después

Una fuga de datos ocurre cuando el entrenamiento incorpora información que no estaría disponible en producción. Ajustar el vocabulario TF-IDF con todos los registros antes de dividir train/test contamina la evaluación.

# CORRECTO
X_tr = vec.fit_transform(textos_train)
X_te = vec.transform(textos_test)
clf.fit(X_tr, etiquetas_train)
pred = clf.predict(X_te)

# INCORRECTO: aprender con el test
X_todos = vec.fit_transform(textos_train + textos_test)

Otro tipo de fuga: incluir el código UNSPSC de la etiqueta dentro de las variables textuales.

S13 · 19 · Dask sí tiene aplicaciones

Tres escenarios donde repartir tareas aporta valor

Caso A · Servicios independientes

Ocho audios o imágenes llegan a una API de transcripción/OCR. Cada solicitud tarda un tiempo principalmente por espera de I/O y puede terminar independientemente.

Secuencial: esperar respuesta 1, luego 2, ..., luego 8. Dask: dos o cuatro workers ejecutan varias solicitudes a la vez. El ahorro se obtiene por concurrencia, siempre respetando cuotas de la API.

Práctica de clase: usamos ocho lotes SECOP y una espera externa simulada de 0,6 s. El script usa Dask real para repartirlos y mide tiempos reales; no afirma estar transcribiendo audios.

Casos B y C · CPU y datos de mayor tamaño

B. Transformaciones pesadas de archivos: convertir imágenes, calcular características acústicas o extraer información por expediente. Cada worker procesa un grupo sin depender de otros; puede utilizar varios núcleos si hay carga suficiente.

C. Datos mayores que la RAM disponible: Dask DataFrame lee Parquet por particiones, filtra y agrega sin reunir todas las filas en un DataFrame local. Puede distribuirlas en varios nodos cuando existe un clúster real.

Conjunto mayor que memoriaProcesar particiones y agrupar resultados
No se trata de que siempre gane

La elección depende del tiempo de cada tarea, número de workers, transferencia, memoria y si se reutiliza el clúster. Enseñaremos al menos un caso favorable y otro donde la sobrecarga puede dominar.

S13 · 20 · Código real de Dask

De una función Python a cuatro workers reales

La función es la misma; cambia el modo de ejecución

from distributed import Client, LocalCluster

# El estudiante puede elegir 1, 2 o 4 procesos.
cluster = LocalCluster(n_workers=2, threads_per_worker=1,
                       processes=True)
client = Client(cluster)

# Ocho lotes independientes del CSV SECOP pequeño:
futuros = client.map(procesar_lote, trabajos, pure=False)
resultados = client.gather(futuros)
print("Resultados:",len(resultados))
print("Workers:",len(client.scheduler_info()["workers"]))
client.close(); cluster.close()

Client: envía solicitudes. Future: representa un resultado aún no materializado. map: envía la misma función a distintos lotes. gather: reúne las respuestas.

Ejecuta el programa completo, no un fragmento

El script ya define procesar_lote, carga hasta 1.000 títulos SECOP y verifica que la salida secuencial sea idéntica a la distribuida. Genera salidas/dask_demostracion_s13.json con los workers reales.

Para ver tareas y progreso: usa --tablero y abre Codespaces → PORTS 8787 Private mientras el script está activo.

Cuando varias tareas independientes consumen suficiente tiempo o deben esperar respuestas, el planificador puede mantener ocupados diferentes workers; medirás el beneficio real en TU Codespace.

Qué mide un cronómetro de Dask y por qué importa

Dos comparaciones, dos preguntas

1. ¿Dask paraleliza? Compara tiempo secuencial con Dask de clúster caliente. Para ocho esperas independientes de 0,6 s, el mínimo ideal es ~4,8 s secuencial, ~2,4 s con 2 workers y ~1,2 s con 4, más coordinación.

2. ¿Vale la pena iniciar Dask? Compara tiempo secuencial con el total de la primera ejecución, que incluye construir el clúster. Puede perder aunque el cómputo paralelo haya ganado.

S13 · 24 · Entrenamiento no es transformación

Por qué XGBoost local ganó y Dask puede seguir siendo útil

Definiciones antes de leer los segundos

fit de TF-IDF: calcula vocabulario e IDF. transform de TF-IDF: convierte textos a vectores. fit de XGBoost: ajusta árboles del modelo con matrices y etiquetas ya preparadas. predict: usa un modelo entrenado para obtener predicciones. Son tareas diferentes y sus cronómetros no deben mezclarse.

Fase medida para 50.000 fichasLocalDaskQué significa
Solo entrenar XGBoost (fit)0,5816 s1,2465 sLocal ganó por 0,6649 s

La VM del runner tenía 4 vCPU y 16 GB RAM como especificación estándar pública. XGBoost local usó 2 hilos y Dask 2 workers de un hilo; el modelo y las rondas fueron los mismos. No se incluyen abrir el clúster, construir matrices ni predecir.

¿Entonces para qué distribuir?

Este entrenamiento es corto y cabe en una máquina: Dask debe sincronizar workers y enviar datos, de modo que sus costos superaron el beneficio de repartir un solo modelo.

Donde sí tiene sentido estudiar Dask: decenas de conversiones/lecturas por archivo, tareas independientes suficientemente lentas, flujos recurrentes con workers ya abiertos o datos que exceden la memoria local.

En clase no volveremos a ejecutar los 50.000. Se mantiene como ejemplo de medición histórica de una fase, no como ejercicio ni como conclusión universal.

Si el entrenamiento fuera mucho mayor o necesitara varias máquinas, la decisión podría cambiar, pero hay que medir ese caso, no prometerlo.

No confundas instrumentos

Un cronómetro de fit de 0,58 s no informa cuánto tarda todo el proyecto en producir un resultado. Dask no es más inteligente por distribuir y LinearSVC o XGBoost no aprenden mejor por usar más workers.

S13 · 26 · Escalabilidad y CPU

Más workers: cuándo sirven, cuándo estorban

Cuatro CPU lógicas no son cuatro equipos

Con una VM de 4 vCPU, configuraciones como 1×4, 2×2 y 4×1 pueden aprovechar recursos de formas diferentes. 8×1 también es posible, pero puede competir por las mismas CPU y consumir más memoria.

Tipo de funciónPrimera opción a ensayarPor qué
Python puro, procesamiento textual2 o 4 procesos × 1 hiloEvita límite del intérprete por proceso
NumPy o bibliotecas con cálculo nativo1 o 2 workers, varios hilosMuchas operaciones liberan el GIL
Servicio externo por archivo2 o 4 workers, respetando cuotaSuperpone esperas de I/O
Datos muy grandes, muchos archivosDask DataFrame, particiones moderadasNo reúne todas las filas en un único proceso

Siempre revisa CPU habilitadas, RAM disponible, duración de tareas y saturación. No es obligatorio que el número de workers coincida con los núcleos.

Criterio profesional

Cuando el tiempo de una tarea es menor que el costo de programarla y enviar sus datos, crear más workers empeora el rendimiento. Cuando las tareas son independientes y suficientemente lentas, Dask puede ayudar.

S13 · 28 · Vectores y reutilización

Qué significa guardar embeddings en caché

Un costo inicial y consultas posteriores

Embedding: convertir un texto en un vector denso usando un modelo, por ejemplo EmbeddingGemma. Caché: guardar ese vector asociado al documento para no calcularlo otra vez cuando el documento no cambie.

  1. Primera indexación: se codifican los 1.000 documentos y se guardan sus vectores.
  2. Segunda consulta: se calcula el vector de la consulta nueva (sí tiene costo), y se compara con vectores de documentos ya guardados.
  3. Consultas siguientes: no se recodifican los mismos documentos; solo las consultas nuevas y los documentos que cambien.

La caché no mejora la calidad de un vector ni acelera su primera generación. Reduce trabajo repetido. Debe invalidarse cuando cambia el texto o el modelo.

Interpretación de la prueba antigua

Experimento interno, 1.000 fichasTF-IDFEmbeddingGemma 2
Codificar los 1.000 textos0,111 s119,898 s
Calidad de la clasificación F1 macro0,451340,47586

Para medir F1 se separaron 800 documentos de entrenamiento y 200 de prueba, pero se generaron los embeddings de los 1.000 documentos. Esta muestra no es el benchmark de 50.000 fichas.

Para enseñar Dask no necesitamos repetir esta prueba. Puede ilustrar trabajos independientes: generar embeddings en lotes, si existe infraestructura que permite concurrencia y se respetan los límites del servicio/modelo.

La calidad y la velocidad varían según hardware, modelos y datos. Ningún tiempo de GitHub Actions representa automáticamente otro computador.

Ejemplo cotidiano

Si una noticia se consulta 100 veces, conviene conservar su embedding y procesar cada nueva pregunta una vez. No recalculas el vector de esa noticia 100 veces.

S13 · 29 · Adaptar la herramienta

De la práctica al procesamiento de archivos reales

Dónde aparece Dask en un pipeline multimodal

  1. Entrada: lote de imágenes, audios, PDFs o particiones CSV/Parquet.
  2. Partición: crea trabajos por archivo o bloques razonables; evita miles de tareas insignificantes.
  3. Transformación: cada worker extrae texto, convierte audio, calcula una huella o vectoriza documentos.
  4. Recolección: reúne resultados pequeños o guarda Parquet sin traer toda la colección a RAM.
  5. Control de fallos: reintenta tareas fallidas sin repetir toda la colección.
  6. Medición: anota tiempos con y sin scheduler, CPU/hilos y memoria.
