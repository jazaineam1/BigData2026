01 · El problema de escala

¿Qué pasa si los datos no caben en memoria?

Experimento de capacidad

Datos
Memoria

¿Por qué importa?

Una tabla puede ocupar más en RAM que en disco: hay estructuras auxiliares, tipos y resultados intermedios.

Procesar por bloques: leer una parte, calcular un parcial y liberar RAM; combinar después. Si intermedios no caben, ciertos operadores pueden escribir temporalmente a disco (spill). Distribuir añade RAM/CPU, pero también comunicación.

Big Data: también importan velocidad, variedad, calidad y coste, no solo cantidad.

Ejemplo: 40 GB en bloques de 5 GB = 8 lecturas ideales, no 40 GB en RAM simultáneamente. Un join puede requerir estructuras adicionales; no garantiza que 5 GB de RAM basten.

Idea clave. Cambia datos y RAM. La comparación es un modelo de capacidad, no una garantía de que una operación quepa.
01 · Escalamiento

¿Aumentamos una máquina o agregamos máquinas?

Vertical · una máquina

Servidor
CPU CPU RAM RAM

Máquina = servidor físico o virtual. Proceso = programa en ejecución con memoria propia. Hilo = flujo de ejecución dentro del proceso. CPU lógica = capacidad de cómputo. Ampliar CPU/RAM reduce comunicación. Tiene límites de hardware y precio; una falla puede afectar toda la ejecución.

Horizontal · varios nodos

Nodo 1
CPU RAM
Nodo 2
CPU RAM
Nodo 3
CPU RAM
Nodo 4
CPU RAM

Agregar máquinas permite repartir trabajo, no fusiona automáticamente sus memorias. Los procesos se comunican por red; el coordinador planifica y puede reintentar tareas fallidas.

Idea clave. Un clúster es un conjunto de máquinas coordinadas; paralelismo significa ejecutar tareas simultáneamente, distribución significa repartirlas entre recursos, posiblemente remotos.
01 · Historia

De MapReduce a Apache Spark

Hadoop MapReduce: trabajos encadenados

Map: calcular parciales
↓
Reduce: combinar parciales
↓
HDFS: guardar resultado
↓
Nuevo trabajo: leer resultado

HDFS (sistema de archivos distribuido de Hadoop) divide y replica archivos. Ejemplo: map cuenta A/B/C por bloque; reduce suma los parciales. Hadoop MapReduce suele materializar resultados entre trabajos; repetirlo en algoritmos iterativos cuesta lecturas y escrituras.

Spark: plan de varias operaciones

Leer datos
↓
Filtrar y transformar
↓
Calcular y combinar
↓
Reutilizar intermedios si conviene

El mismo conteo puede encadenarse con otro cálculo sin guardar obligatoriamente cada resultado intermedio. Nació en Berkeley (2009); utiliza memoria, disco y red. Puede optimizar varias operaciones y reutilizar datos, sin requerir Hadoop.

Idea clave. Spark no es exclusivamente en memoria ni siempre más rápido. Su ventaja es un motor flexible para consultas, flujos e iteraciones.

03 · Arquitectura

Construyamos una aplicación Spark: el executor

Construye un clúster clásico de ejemplo

Infraestructura ≠ procesos ≠ datos

Driver: proceso coordinador de la aplicación; prepara planes, asigna tareas a executors y recibe estados/resultados.

Cluster Manager: servicio que asigna recursos (p. ej. Kubernetes, YARN o Standalone); facilita iniciar procesos.

Worker: nodo físico/virtual con CPU, RAM y disco. Puede alojar varios executors.

Executor: proceso de una aplicación Spark, normalmente JVM, que ejecuta varias tareas, conserva intermedios en RAM/disco y reporta resultados. Se inicia al asignar recursos y se libera al terminar o por gestión dinámica.

Task: trabajo sobre una partición en una etapa. Al fallar, puede reintentarse; si se pierde un intermedio, Spark puede recomputarlo mediante linaje.

Idea clave. Ejemplo clásico, 1 CPU por tarea; cada nodo dispone de 12 CPU y 32 GB ilustrativos, cada executor 4 GB. No son recursos observados en Databricks.

03 · Datos distribuidos

Una partición es una porción lógica de datos

Divide 12 registros

¿Qué cambia y qué se conserva?

Una partición es una unidad de datos que puede procesarse por separado. Cada tarea procesa una partición dentro de una etapa.

Una partición es lógica, no un archivo ni una máquina. Cuando se ejecuta una tarea, un executor lee su partición desde la fuente o recibe intermedios. Una tabla de 12 filas sigue teniendo 12 filas.

Linaje = receta de operaciones; si se pierde un bloque recomputable, puede reconstruirse desde la fuente. El reparto real depende de claves y estrategia; puede ser desigual.

Idea clave. Separar los datos permite distribuir el cálculo. Todavía no hemos cambiado los registros.

03 · Ejecución paralela

¿Cuántas tareas caben al mismo tiempo?

Simula un executor y seis tareas

Ranura (slot) = capacidad para una tarea

Imagina puestos de trabajo: las tareas esperan en cola, ocupan un puesto mientras se ejecutan y lo liberan al terminar.

CPU: recurso de cálculo. Partición: datos. Tarea: trabajo sobre una partición en una etapa. Ranura: capacidad disponible para ejecutar una tarea.

4 CPU y 1 CPU/tarea → 4 ranuras; 4 CPU y 2 CPU/tarea → 2 ranuras. En el clúster, suma las ranuras de cada executor: no puedes combinar CPU de dos procesos para una tarea. Spark 4.0 usa 1 CPU/tarea por defecto (spark.task.cpus).

Un job puede tener varias etapas; cada etapa tiene tareas. La capacidad real también depende de RAM, recursos adicionales y planificación.

Prueba: 6 tareas con 2 ranuras requieren 3 rondas ideales; con 3 ranuras, 2. Las rondas suponen igual duración y no miden tiempos reales.

03 · Comunicación y coste

Shuffle: ¿por qué mover datos puede ser costoso?

Experimento de intercambio

Cuatro fenómenos diferentes

Shuffle: datos/parciales se escriben, transfieren y leen según clave. Puede usar red y disco. Un filtro local normalmente no lo requiere.

Broadcast: copiar una dimensión pequeña a los ejecutores para unir localmente con la tabla grande; no requiere reorganizar esa tabla para la unión.

Skew (desbalance): una clave concentra datos; una tarea lenta puede retrasar la etapa completa.

Spill (derrame a disco): ciertos operadores escriben temporalmente estructuras que no caben en memoria; añade I/O, no implica pérdida de filas.

Prueba los pasos: intercambio → unión con broadcast → desbalance → spill. Las cantidades son ilustrativas, no mediciones.

Idea clave. Spark puede agregar parciales antes del intercambio. No todos los joins necesitan shuffle. El optimizador elige o adapta estrategias.

04 · Planificación y ejecución

Del código PySpark a jobs, stages y tasks

Construye una consulta realista

df.filter(...).groupBy(...).agg(...).show()

De intención a ejecución

Transformación: describe un nuevo DataFrame. Acción: solicita el cálculo (show, count, write). Leer esquema/metadatos puede realizar trabajo antes.

Plan lógico: qué calcular. Catalyst: reescribe el plan, por ejemplo adelanta filtros y elimina columnas que no se necesitan.

Plan físico: operadores concretos (Scan, Filter, Aggregate, Exchange). AQE: ajusta algunas decisiones con estadísticas de ejecución, como juntar particiones o cambiar una unión.

DAG: grafo dirigido sin ciclos de dependencias. Job: trabajo solicitado; stage: fase con tareas que pueden ejecutarse sin otro intercambio; task: trabajo sobre una partición.

Idea clave. Una acción puede iniciar uno o varios jobs. Un operador no es una máquina. El plan real y las etapas dependen de Spark y AQE.

05 · Almacenamiento

¿Dónde conservamos la información?

Data Warehouse · almacén

OLTP = registrar contratos uno a uno; OLAP = analizar grandes conjuntos históricos. Warehouse integra tablas para preguntas como cobertura anual por departamento; no es la fuente transaccional.

Data Lake · lago

Ejemplo SECOP: conservar JSON, PDF de actas, OCR, audio y Parquet con procedencia. Permite reutilización; necesita catálogo y reglas para evitar desorden.

Lakehouse

Lakehouse conserva archivos abiertos y añade tablas con esquema, transacciones y permisos; permite analizar y entrenar sobre datos reutilizables. Puede utilizar el mismo dato para SQL y ML.

Idea clave. Un archivo no equivale a una tabla gobernada. Schema-on-read interpreta estructura al leer; schema-on-write aplica reglas al escribir. Separar cómputo y almacenamiento permite escalarlos de forma distinta.

06 · Persistencia

Delta Lake: ¿qué sucede cuando cambia una tabla?

Recorre las versiones

Parquet no es Delta Lake

Parquet: archivos columnares: guardan valores, no una historia de tabla. Delta: archivos de datos + registro _delta_log que registra archivos agregados y retirados lógicamente por cada commit. Leer versión anterior utiliza el conjunto de archivos de esa versión si aún existen.

ACID: atomicidad (todo o nada), consistencia (reglas), aislamiento (concurrencia) y durabilidad (cambios confirmados).

Append agrega, overwrite reemplaza, MERGE actualiza/inserta. Time travel consulta versiones conservadas, no es un backup perpetuo.

MLlib: ¿cómo aprenden juntos los executors?

¿Qué es MLlib y para qué sirve?

Es la biblioteca de aprendizaje automático de Spark. Trabaja con DataFrames mediante pyspark.ml: prepara características, entrena, predice y evalúa.

ProblemaAlgoritmo disponible
Predecir una categoríaRegresión logística, Random Forest
Predecir un númeroRegresión lineal
Encontrar gruposK-means
Recomendar elementosALS

Caso: clasificar descripciones de compras: 0 = bien, 1 = servicio. El modelo recibe características numéricas y aprende pesos comunes. Cada executor calcula contribuciones sobre sus filas; el algoritmo combina parciales. fit aprende, transform predice sin reajustar.

Simula una iteración del aprendizaje

4 ejemplos, 2 particiones; x = señal numérica (−1 o +1), y = clase real. Peso w inicial = 0.

Pérdida: mide error de probabilidades. Gradiente: cambio de esa pérdida respecto al peso. Se combinan sumas y cantidades; el modelo recibe un único peso actualizado.

Idea clave. MLlib puede repartir cálculos del ajuste sobre particiones. La simulación usa descenso de gradiente escalar sin intercepto ni regularización; no es el optimizador real de Spark.
